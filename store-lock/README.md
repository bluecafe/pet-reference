# store-lock

로컬 파일에 둔 기억을 안전하게 다루는 최소 예제입니다.

기억하는 기능을 만들면 반드시 두 가지가 따라옵니다 — **두 프로세스가 같은 파일을 열었을 때**와 **되돌릴 수 없는 삭제**입니다.

> 블로그 글: (발행 후 링크)

## 돌려보기

```bash
cargo test    # 잠금 배타성·권한·삭제 확인 검증
cargo run     # 두 번째 접근이 막히는 과정을 순서대로 출력
```

의존성이 없습니다. `flock(2)`을 직접 선언해 씁니다.

```text
1) 첫 번째가 잠금을 잡는다        → 성공
2) 두 번째가 기다리지 않고 시도    → 빈손. 이미 잡혀 있다
3) 첫 번째가 놓는다              → 두 번째가 이제 잡는다
```

## 판단이 갈리는 곳 네 군데

### 삭제는 불리언이 아니라 문자열로 받는다

```rust
require_delete_confirmation("DELETE")?;
```

`"DELETE"`만 통과합니다. 소문자도, 공백이 붙은 것도 거절합니다.

`clear(scope, true)` 같은 형태였다면 다른 플래그를 복사하다 실수로 `true`가 들어갈 수 있고, 무엇보다 **호출하는 쪽 코드만 봐서는 그 `true`가 무슨 뜻인지 안 보입니다.** `"DELETE"`는 우연히 만들어지지 않습니다.

### 지우는 범위를 나눈다

대화만, 선호만, 관계만, 전부. **전부 아니면 전무로 두면 사용자는 전부를 고를 수밖에 없습니다.**

### 잠금을 못 걸면 저장하지 않는다

`flock`이 실패하거나 지원되지 않는 환경에서는 `StorageUnavailable`로 끝냅니다. **잠금 없이 그냥 쓰는 경로가 없습니다.**

만들다 보면 "잠금은 부가 기능이고 저장이 본체"라고 생각하기 쉽습니다. 그러면 잠금 실패를 무시하고 저장을 진행하게 됩니다. 이 코드는 반대로 봅니다 — 안전하게 못 쓸 바에는 안 씁니다.

### 거는 쪽은 엄격하고 푸는 쪽은 느슨하다

해제는 `unlock_best_effort`입니다. 실패해도 넘어갑니다.

이 시점에서는 오류를 돌려줄 곳도 없고 다시 시도해 봐야 같은 결과입니다. 게다가 프로세스가 끝나면 OS가 정리합니다. **거는 실패는 데이터를 지키기 위해 멈출 이유가 되지만, 푸는 실패는 멈춘다고 나아지지 않습니다.**

## 파일 권한

잠금 파일을 `0o600`으로 엽니다. 대화 기록이 들어가는 자리라 기본 권한에 맡기지 않습니다 — 기본값은 시스템 설정에 따라 달라지고, 달라지면 같은 기계의 다른 계정이 읽을 수 있습니다.

테스트가 실제 권한 비트를 확인합니다.

## 원본과 다른 점

앱에서는 잠금이 **두 겹**입니다. 프로세스 안 잠금이 같은 앱의 다른 스레드를 막고, OS 파일 잠금이 다른 프로세스를 막습니다. 한 겹만으로는 부족합니다 — 프로세스 안 잠금은 다른 프로세스를 모르고, 파일 잠금은 같은 프로세스의 스레드를 막아 주지 않습니다.

이 예제는 **바깥쪽 한 겹만** 남겼습니다. Windows는 `LockFileEx`를 쓰지만 여기서는 Unix만 구현하고, 그 외 환경은 저장을 거절합니다.
