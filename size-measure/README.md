# size-measure

번들에서 무엇이 얼마나 차지하는지 재는 최소 예제입니다.

"앱이 무겁다"는 감이고 "이 파일이 9.8M"은 숫자입니다. 줄이려면 뒤가 필요합니다.

> 블로그 글: (발행 후 링크)

## 돌려보기

```bash
cargo test                          # 측정 규칙 7개
cargo run -- ~/Downloads/Some.app   # 실제 번들 측정
cargo run                           # 인자가 없으면 현재 폴더
```

의존성이 없습니다.

## 실제로 재본 것

이 앱의 에셋 폴더입니다.

```text
  파일        3
  논리 합계          9.9M   (ls 가 보여주는 값)
  디스크 사용        9.9M   (du 가 보여주는 값)

확장자별
  png               9.8M   99.7%  1개
  json             32.0K    0.3%  2개

큰 파일
       9.8M  sprite-sheet-alpha.png
      24.0K  manifest.json
```

**스프라이트 시트 한 장이 99.7%입니다.** 매니페스트를 아무리 줄여도 의미가 없다는 뜻입니다. 이런 건 재보기 전에는 모릅니다.

## 재는 일이 갈리는 곳 세 군데

### `ls`와 `du`가 다른 값을 준다

파일 시스템은 **블록 단위로** 자리를 줍니다. 1바이트짜리 파일도 블록 하나를 차지합니다.

그래서 작은 파일이 많으면 논리 크기 합계보다 실제 사용량이 훨씬 큽니다. 테스트에 1바이트 파일 열 개를 넣어 이 차이를 확인합니다 — 논리 합계는 10바이트인데 디스크 사용량은 그보다 큽니다.

배포 크기를 볼 때는 논리 크기가, 디스크 여유를 볼 때는 사용량이 맞습니다. 둘 다 보여줍니다.

### 심볼릭 링크를 따라가면 두 번 센다

`.app` 번들의 `Frameworks` 아래에는 버전 폴더를 가리키는 링크가 여러 개 있습니다. 따라가면 같은 것을 몇 번씩 세고, 링크가 밖을 가리키면 **번들 밖의 크기까지 합쳐집니다.**

`symlink_metadata`로 링크 자체를 보고 따라가지 않습니다.

### 하드링크는 실체가 하나다

여러 경로에서 보이지만 디스크에는 한 번만 있습니다. 경로마다 세면 실제보다 큰 값이 나옵니다.

`(기기, inode)` 쌍을 기억해 두 번째부터는 건너뜁니다.

## 확장자별로 묶는 이유

무엇을 줄여야 하는지는 대개 여기서 나옵니다. 파일 목록을 훑는 것보다 "png가 99.7%"가 한 줄로 답을 줍니다.

큰 파일 목록은 상위 10개만 보여줍니다. **전체 목록은 사람이 못 읽습니다.**

## 여기 없는 것

**압축 후 크기.** 배포하는 것은 ZIP이라 실제로 압축해 봐야 압니다. 텍스트는 크게 줄고 PNG는 거의 안 줄어서, 압축 전 비율과 압축 후 비율이 다릅니다.

**바이너리 내부 구성.** 실행 파일 안에서 무엇이 자리를 차지하는지는 심볼 테이블을 읽어야 합니다. 이 예제는 파일 단위까지만 봅니다.
