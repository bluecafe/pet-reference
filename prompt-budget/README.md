# prompt-budget

컨텍스트가 좁은 로컬 모델에 넣을 프롬프트를 예산에 맞춰 자르는 최소 예제입니다.

핵심은 자르는 기술이 아니라 **버리는 순서**입니다. 넣을 것은 여섯 가지인데 예산은 하나뿐이라, 무엇을 먼저 포기하느냐가 곧 캐릭터의 품질이 됩니다.

> 블로그 글: (발행 후 링크)

## 돌려보기

```bash
cargo test    # 버리는 순서가 규격대로인지 검증
cargo run     # 예산을 좁혀 가며 무엇이 먼저 사라지는지 출력
```

의존성이 없습니다.

## 버리는 순서

```text
1  최근 대화      오래된 것부터
2  예시           최신 것부터
3  선호           최신 것부터
4  요약           잘라 맞추고, 안 되면 비운다
5  페르소나        잘라 맞추고, 안 되면 비운다
   ─────────────────────────────
   사용자의 현재 입력은 자르지 않는다
```

`cargo run` 출력이 이 순서를 그대로 보여줍니다.

```text
      예산     대화↓    예시↓    선호↓      요약B    페르소나B
     914       0      0      0      192      464
     878       3      0      0      192      464   ← 대화가 먼저 사라진다
     835       3      2      0      192      464   ← 그 다음 예시
     788       3      2      2      192      464   ← 그 다음 선호
     577       3      2      2        0      464   ← 요약이 비어도 페르소나는 남는다
     113       3      2      2        0        0
     110  더 버릴 것이 없다 → 실패로 끝낸다
```

## 판단이 갈리는 곳 네 군데

### 목록마다 자르는 방향이 다르다

대화는 `remove(0)`으로 **앞에서**, 예시와 선호는 `pop()`으로 **뒤에서** 뺍니다.

대화는 시간순이라 앞이 오래된 것입니다. 방금 한 말을 버리고 어제 한 말을 남기면 대화가 어긋납니다. 예시와 선호는 시간순이 아니라 앞쪽에 중요한 것이 오도록 넣어 둔 목록이라 반대입니다.

**목록이라고 다 같은 방향으로 자르면 안 됩니다.** 그 목록의 앞이 무엇을 뜻하는지를 봐야 합니다.

### 사용자 입력은 자르지 않는다

넘치면 줄이는 게 아니라 **거절합니다**(`UserTextTooLarge`).

질문을 잘라서 넣으면 모델은 잘린 줄 모르고 성실하게 답합니다. 사용자는 자기가 하지 않은 질문의 답을 받습니다. "너무 깁니다"가 낫습니다.

### 페르소나가 마지막이다

캐릭터의 정체성을 가장 늦게 버립니다. 그마저 안 되면 실패로 끝냅니다 — **빈 캐릭터로 답하느니 답하지 않습니다.**

### 페르소나도 신뢰하지 않는다

`render()`가 프롬프트를 신뢰 구간과 비신뢰 구간으로 나누는데, 페르소나와 예시도 비신뢰 쪽입니다. 앱이 들고 있는 값이라 안전해 보이지만 사용자가 편집할 수 있고, 편집할 수 있으면 거기에 지시문을 적을 수 있습니다.

## 원본과 다른 점

앱에서는 JSON 직렬화, 마크업 이스케이프, 응답 스키마가 함께 붙어 있고 덩어리를 줄일 때 이진 탐색으로 정확히 맞춥니다. 여기서는 **순서를 보여주는 데 필요한 만큼만** 남기고 절반씩 줄이는 방식으로 단순화했습니다.
