# macos-unsigned

애플 개발자 계정 없이 배포한 macOS 앱이 왜 **"손상되었기 때문에 열 수 없습니다"**로 나오는지, 그 표시가 실제로 어디에 붙어 있는지 직접 보는 예제입니다.

앱이 깨진 게 아닙니다. `com.apple.quarantine`이라는 확장 속성 때문입니다.

> 블로그 글: (발행 후 링크)

## 돌려보기

```bash
cargo test                          # 속성 읽기·쓰기·지우기 검증 (7건)
cargo run                           # 가짜 번들로 단계별 시연
cargo run -- ~/Downloads/Some.app   # 실제 경로 검사 (읽기만 한다)
```

의존성이 없습니다. `getxattr`·`setxattr`·`removexattr`를 직접 선언해 씁니다. macOS 전용입니다.

## `-r`이 왜 필요한가

`cargo run` 출력입니다.

```text
1) 갓 빌드한 상태          격리된 항목 0   → 만든 사람 기계에서는 잘 열린다
2) 다운로드된 상태          격리된 항목 2   → 받은 사람 기계에서 막힌다
3) 최상위만 지움            격리된 항목 1   → 안쪽 실행 파일에 남아 여전히 안 열린다
     남음: .../Contents/MacOS/app
4) 재귀로 지움              격리된 항목 0   → 이제 열린다
```

**`.app`은 파일 하나가 아니라 디렉터리입니다.** 그래서 격리 표시도 안에 있는 파일마다 붙습니다. `xattr -cr`의 `-r`이 재귀라는 뜻이고, 그게 없으면 3번 상태에서 멈춥니다.

## 왜 만든 사람은 모르는가

1번이 문제의 핵심입니다. **직접 빌드한 앱에는 격리 표시가 없습니다.** 인터넷에서 받은 게 아니기 때문입니다.

그래서 만든 사람 기계에서는 잘 열리고, 받은 사람 기계에서만 막힙니다. 배포하기 전에는 재현되지 않습니다.

## 격리 속성의 값

세미콜론으로 나뉜 네 칸입니다.

```text
0081;68a1b2c3;Safari;1A2B3C4D-5E6F-...
플래그  시각   받아온 프로그램   이벤트 ID
```

형식이 문서화돼 있지 않아 실제 값을 보고 맞췄습니다. **칸이 모자라도 실패로 처리하지 않습니다** — 여기서 멈추게 만들면 macOS가 형식을 바꿀 때 도구가 통째로 죽습니다.

## 판단이 갈리는 곳 세 군데

### 속성이 없는 것은 오류가 아니다

대부분의 파일에는 원래 격리 표시가 없습니다. `getxattr`가 실패해도 "없음"으로 다룹니다.

반면 **지우기는 없으면 실패합니다.** 도구는 이걸 "이미 깨끗함"으로 해석해야 합니다. 테스트에 이 차이를 넣어 뒀습니다.

### 심볼릭 링크는 따라가지 않는다

번들 안에는 링크가 흔합니다. 따라가면 같은 파일을 여러 번 보거나 번들 밖으로 나갑니다. `XATTR_NOFOLLOW`와 `symlink_metadata`를 쓰는 이유입니다.

### 읽기만 하고 지우지 않는다

`cargo run -- <경로>`는 검사만 합니다. 남의 파일을 말없이 고치지 않습니다.

지우는 함수(`clear_bundle`)는 있지만 시연 모드에서 자기가 만든 임시 번들에만 씁니다.

## 여기 없는 것

**서명과 공증.** 애드혹 서명 여부는 `codesign -dv --verbose=2`로 봅니다. 이 예제는 격리 속성만 다룹니다 — 서명 검사는 `Security.framework`을 불러야 해서 예제가 두 배가 됩니다.

세 단계의 차이는 이렇습니다.

| 상태 | 사용자가 보는 것 |
| --- | --- |
| 개발자 서명 + 공증 | 그냥 열린다 |
| 개발자 서명만 | 경고 후 우클릭 열기로 통과 |
| 애드혹 서명 (계정 없음) | "손상되었기 때문에 열 수 없습니다" |
